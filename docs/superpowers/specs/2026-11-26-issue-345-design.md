# Web-App über den Browser installierbar machen (PWA mit minimalem Service Worker)

> **Ursprünglicher Wunsch (Daniel, 26.11.):** Auf Android lässt sich Foodly aus dem Browser nicht als App installieren, nur als Verknüpfung, die im Browser öffnet (getestet mit Brave). Die Web-App soll über einen Browser installierbar sein.

## Context
Phase 6 (M5) hat ein PWA-Manifest (`public/manifest.webmanifest`, Icons in `public/icons/`) angelegt, **ohne Service Worker**. Chromium-Browser bieten dann meist nur „Zum Startbildschirm hinzufügen“ (Verknüpfung) statt „App installieren“. Die native App (Phase 7, Capacitor) ist davon unabhängig.

## Goal
Die Web-App erfüllt die Installierbarkeits-Kriterien von Chrome (Android und Desktop), sodass der Browser „App installieren“ anbietet und Foodly danach als eigenständige App (standalone, eigenes Icon im App-Drawer) startet.

## Behaviour
- Chrome auf Android bietet im Menü „App installieren“ (bzw. den Install-Hinweis) an; die installierte App öffnet ohne Browserleiste.
- Ein minimaler Service Worker wird registriert, **nur** im Web-Produktionsbuild (nicht in `vite dev`, nicht im Native-Build `--mode native`/Capacitor, nicht in Tests).
- Kein Offline-Modus: der Service Worker cacht keine API-Antworten. Netzwerk-Requests gehen unverändert ans Netz (pass-through `fetch`-Handler oder gar keiner, je nachdem, was Chrome aktuell verlangt).
- Updates: Ein neues Deployment wird beim nächsten Laden wirksam; der Service Worker darf keine alten App-Versionen festhalten (kein Precache des App-Shells, oder sauberes skipWaiting/clients.claim).
- Funktioniert auch unter einem Unterpfad (`base` aus `buildBase`, z. B. Skaile-Preview `SKAILE_PREVIEW_BASE`): Manifest-Link, Service-Worker-URL und Scope richten sich nach `base`.
- iOS/Safari: unverändert (Teilen → Zum Home-Bildschirm), darf nicht schlechter werden.

## Acceptance criteria
1. Produktionsbuild (`npm run build` + `vite preview`) registriert genau einen Service Worker; Chrome DevTools → Application → Manifest zeigt keine Installierbarkeitsfehler.
2. `vite dev` und `npm run build:native` registrieren keinen Service Worker (Test oder Build-Prüfung belegt das; Native-`dist/` enthält keine SW-Registrierung bzw. sie ist per `isNative()`/Mode abgeschaltet).
3. Der Service Worker cacht keine Antworten von `VITE_API_URL`/`/api/` und keine HTML-Shell; nach einem neuen Build lädt die Seite beim Reload die neue Version (Test oder dokumentierte Prüfung).
4. Manifest-Link und SW-Pfad funktionieren mit `base` ≠ `/` (Test auf Basis von `buildBase`).
5. Manifest enthält alles, was Chrome für die Installation braucht (name/short_name, start_url, display standalone, Icons 192 + 512, ggf. `id`); vorhandene Icons werden genutzt.
6. Entry-Chunk-Limit (aktuell 712 kB) wird eingehalten; alle bestehenden Checks grün.
7. `docs/` (z. B. `docs/native.md` oder ein kurzer Abschnitt in README/architecture) beschreibt: Web-App installierbar über Chrome, kein Offline-Modus, Abgrenzung zu Phase 8 und zur nativen App.

## Non-goals
- Offline-Modus, Caching von Rezepten/Bildern, Background-Sync (Phase 8).
- Eigener Install-Button/Banner in der UI.
- Store/APK (E3), Änderungen an der Capacitor-App.
- Garantien für Brave/Firefox (Browser-Verhalten außerhalb unserer Kontrolle); Ziel ist Chrome und Samsung Internet.

## Assumptions
- Handgeschriebener Mini-Service-Worker in `public/` oder `vite-plugin-pwa` mit deaktiviertem Precache – Wahl dem Worker überlassen, kleinere Abhängigkeit bevorzugt.
- Produktions-Hosting ist HTTPS (Voraussetzung für Service Worker).

## Affected areas
- `public/manifest.webmanifest`, `public/` (neuer `sw.js`) oder `vite.config.ts` (Plugin)
- `index.html` (Manifest-Link ist absolut `/manifest.webmanifest` – mit `base` prüfen)
- `src/main.tsx` (Registrierung), `src/native/platform.ts` (`isNative()`), `src/nativeBuild.ts` (`buildBase`)
- Docs
